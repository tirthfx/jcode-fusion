## 2. Merge-back (Phase 2, third and final slice)

**The gap closed**: Session 1 shipped worktree creation and cleanup; a spawned swarm worker's commits lived only on its own branch with no path back into the coordinator's tree.

**Design** (published as a side-by-side Claude Artifact before writing code, per the user's explicit request — IBM Plex type family, verdigris/blueprint palette, chosen deliberately to avoid AI-design clichés):

### The git push mistake (worth remembering precisely)

`git push origin fusion-main` (no explicit refspec) created a **new** branch literally named `fusion-main` on the remote, separate from `main` — because the local `fusion-main` branch tracks `origin/main` (a deliberate rename from Session 1: local and remote branch names deliberately differ on this repo), and a bare `git push origin fusion-main` pushes to a remote branch of the *same name*, not the tracked upstream. Caught via `git branch -vv` showing "ahead 1" instead of "up to date" after a supposedly-successful push, and `git ls-remote --heads origin` showing both a stale `main` and a stray new `fusion-main`. Fixed: `git push origin fusion-main:main` (explicit refspec) landed the commit correctly, then `git push origin --delete fusion-main` removed the stray branch.

**Standing rule for this repo, worth repeating in every session**: `git push` (bare, relying on the configured upstream) or `git push origin fusion-main:main` (explicit) are both safe. A bare `git push origin fusion-main` is not, because local and remote branch names don't match. Verify with `git branch -vv` after any push — it should say `[origin/main]` with no "ahead", not just that the push command exited 0.

## 7. The live-credentialed test (first real attempt, ever, across all sessions)

Every prior session's notes — repeatedly, explicitly — called this "the single biggest unverified assumption in the whole project," and one autonomous `/loop` iteration even fabricated a false claim that it had already happened (caught and corrected earlier in `PROGRESS.md`, before this session's own attempt). A genuine live-credentialed run needs real credentials, but this project's other standing, explicit rule is **never touch the user's real `~/.jcode` install**. Asked the user directly (`AskUserQuestion`, two sub-questions: how to source credentials, and how much the test should actually do) rather than picking a side myself, since both a wrong assumption about acceptable risk and an unnecessary blocker were plausible. The user chose: copy credentials into an isolated directory (never modify the real install), and keep the test scope to a minimal smoke prompt.

**What was actually done**: created `/tmp/jcode-fusion-live-test/` (mode 700), copied (never moved, never modified the source) `~/.jcode/auth.json`, `auth-refresh-state.json`, and `antigravity_oauth.json` into it, then ran real commands against that isolated `JCODE_HOME`:
- `jcode-fusion auth status` — genuinely informative, not fabricated: `claude`'s real OAuth token is actually **expired** in the user's real install (`invalid_grant`, refresh failed 17 days ago — predates this entire project, unrelated to anything Fusion did), `gemini`/`openai`/everything else was never configured at all, and `antigravity` was the one live, working, authenticated credential.
- `jcode-fusion run "say hello..." -p antigravity` — reached the real Google Antigravity API for real and got a real, structured `HTTP 429 RESOURCE_EXHAUSTED` response back.

**The investigation that followed is the actually valuable part, not just the 429 itself.** Initial assumption (quota exhaustion from this session's own heavy `agy` usage) was checked, not assumed — and disproven: the user's real Google AI Pro dashboard showed 93–100% of every quota bucket remaining, and `jcode-fusion usage` independently agreed (every single Antigravity model listed at 0% used). Retried anyway (still 429); retried with an explicit safe fallback model, `gemini-3-flash` (still 429); then isolated the actual variable: ran `agy` directly against the *same account* and it succeeded instantly with a real response ("Hi."). **This proved the 429 is specific to jcode-fusion's own request, not the account.**

Found a concrete, real lead in the source: `crates/jcode-provider-antigravity/src/lib.rs` (confirmed **upstream** jcode code via `git diff v0.81.2`, not Fusion's) hardcodes every Antigravity request's client-identity header as `X_GOOG_API_CLIENT = "google-cloud-sdk vscode_cloudshelleditor/0.1"` — self-identifying as the Antigravity IDE / Cloud Shell Editor product specifically. Working hypothesis, not yet confirmed: Google's backend may quota by `(account × client-product-identity)`, not just account-wide, so this specific product identity could have its own separate, currently-constrained allowance invisible to both the account dashboard and jcode's own usage tracker. Also found and correctly *ruled out* an unrelated, pre-existing bug in that same file (`remap_unsupported_model`'s `gemini-3.1-pro-high` → `gemini-pro-agent` fixup) — that one causes HTTP 400, not 429, so it's not the cause here, just a nearby red herring worth not confusing with the real issue.

**Stopped at 4 real attempts, deliberately** — once the actual pattern was isolated (jcode-fusion fails consistently, `agy` on the identical account succeeds instantly, both quota dashboards say there's plenty of room), further blind retries against the same apparently-gated resource weren't going to add signal.

**Full detail recorded in `PROGRESS.md`** (not duplicated fully here) — that's now the authoritative record of this finding; treat this file as the narrative companion to it, not a competing source.

**What's still genuinely unverified**: an actual successful, completed model response through jcode-fusion itself. The real credential/network/request/error-handling path is now proven to work end to end (a completed error round-trip *is* meaningful verification of the plumbing) — a full completed turn with real tool calls, a real swarm spawn, or a real `apply` merge-back under live load is still the next real gap, blocked on either resolving the 429 (try a different provider, or investigate the client-identity hypothesis further) or a fresh login to a provider that isn't `antigravity`.

- **`agy` is genuinely useful and genuinely verified to work as described**, not just claimed — both for code review (two real, independently-caught bug fixes came directly from `agy` review passes this session) and for large-scale orchestrated research (the 7-way parallel repo scan). This bit once this session (see §6) and is an easy, silent way to corrupt a commit message or (worse) execute unintended shell commands.
- **The `git push origin fusion-main` vs `git push origin fusion-main:main` distinction is real and will bite again** if not checked — verify with `git branch -vv` after every push, not just a zero exit code.
- **`tool::bash::tests::*` in `bash_tests.rs` has a real, pre-existing flaky-test class** (unguarded global `HOME` env var mutation across parallel test threads) — confirmed twice this session via `git stash` comparison. Worth a dedicated cleanup pass at some point (wrap the affected tests in `crate::storage::lock_test_env()`, matching every other properly-isolated test in this codebase), but explicitly out of scope for a findings-fixing pass.
- **When investigating a live-API discrepancy, isolate the variable before hypothesizing** — the quota-exhaustion assumption was reasonable given this session's own heavy usage, but checking the actual dashboards first (rather than assuming) and then isolating jcode-fusion vs. `agy` on the *same account* is what actually found the real, more specific, more useful signal (a jcode-specific client-identity issue, not generic exhaustion).

**The last remaining piece of the whole project — ACP gap #7, routing `WriteTool`/`ReadTool` through the client-callback relay**: shipped this continuation, and it was the most eventful slice of the whole session for real, caught-before-shipping bugs.

- **The original design was replaced mid-flight after an agy review found it genuinely broken, not just imperfect**: `mark_session_as_acp`, a sticky `HashSet<String>` set once at ACP session creation and never cleared, plus a new `Request::MarkAcpSession` wire message to set it. Real bug: an ACP client that disconnects and is later resumed by a *different* client (a TUI, via `session/resume`) would keep the stale mark, permanently routing that now-ordinary session's file I/O through a dead callback — every read/write hangs for the timeout and fails, forever, until process restart. **Fixed** by making `is_acp_session` a live, async lookup against `client_connections` (the daemon's existing, already-correct per-connection tracking) instead of a separate, staleness-prone mark — self-corrects on disconnect/resume automatically. This removed the entire `Request::MarkAcpSession` mechanism as unnecessary (confirmed fully gone via repo-wide grep before calling it done).
- **A second, self-inflicted bug, found by direct reproduction, not review**: after the redesign compiled clean, the new ACP-routing tests in `write.rs`/`read.rs` passed individually but **hung indefinitely when run together** (`cargo test`'s default concurrent scheduling). Root-caused via `sample` process profiling, not guesswork: the test helpers registering the shared `OnceLock` maps raced — the loser of a concurrent `set()` (silently ignored) kept its own orphaned local map instead of the real global one, so its session id was invisible to the production lookup, and the test hung forever on `event_rx.recv()` waiting for an event that could now never be sent. Fixed by having both helpers re-read the *actual* global after attempting to set it, regardless of who won the race. Verified by reproducing the hang 100% of the time before the fix (5 runs, every run hung) and its complete absence after (5/5 clean runs).
- **A follow-up agy review of the whole 832-line redesign diff** came back with 5 findings, all checked against real code, none requiring further changes (a suggestion to verify `MarkAcpSession` was fully pruned — confirmed via grep; the rest were already-documented, deliberately-accepted limitations).
- Full detail, including the exact code and reasoning: `PROGRESS.md`'s "Phase 3, ACP gap #7 closed" section.

**Then, with every phase now shipped, the user's original standing instruction — "after everything is complete, I want a full repository tests done by Gemini pro models with higher efforts" — was executed as the true final step.** Not a re-scan of the whole repo (the 2026-08-30 scan in §5–6 already covered and triaged that), but a focused, whole-subsystem review of everything shipped *since* that scan (all of Phase 3's ACP work, all of Phase 4). Two parallel `agy` (Gemini 3.1 Pro, high effort) passes, each explicitly asked to hunt for cross-slice interaction bugs no single slice's own review would catch — and it worked exactly as intended:

1. **ACP callbacks silently routed to the wrong client on a multi-client session.** `send_acp_callback` resolved a session's channel via `SwarmMember::event_tx` — last-writer-wins across *every* client that attaches to that session (confirmed via reading `client_session.rs`'s real `Subscribe` handling: it unconditionally overwrites `event_tx` on each new attachment). A TUI opened to monitor an already-ACP-connected session — an entirely ordinary jcode workflow — would silently hijack routing if it attached after the ACP client. Fixed by resolving the *specific* ACP client's own channel via `client_connections` + `SwarmMember::event_txs` (a per-connection map that already existed, unused for this). The old generic function had no real caller left and was **deleted outright** (with its tests retargeted onto a shared `send_acp_callback_via_sender` helper) rather than kept as dead code that a future caller could reach for and reintroduce the exact bug. A **follow-up review of this exact fix** caught one more, lower-severity gap: `HashMap::values().find_map(...)` picks an unspecified client among multiple simultaneous ACP connections on one session — fixed with `min_by_key(connected_at)` for a deterministic, earliest-attached choice.
2. **A real leak under lock contention in the ACP adapter's own pending-request cleanup**, `src/cli/acp.rs`. `PendingRequestGuard::drop` used `tokio::sync::Mutex::try_lock()` — which fails whenever the lock is contested by *anything*, not just the same id being completed elsewhere, silently skipping cleanup and leaking the entry forever under real concurrent traffic. Fixed by switching to a plain `std::sync::Mutex` (verified: never held across an `.await` anywhere in the file). A new 64-task concurrency stress test proves the pending map ends up provably empty.
3. **A too-short session could be permanently, silently excluded from ambient mode's own crash-recovery safety net**, `memory_consolidation.rs`. Marking a too-short session `Extracted` forever assumed "too few messages" always means "finished" — but it could just as easily be a session caught mid-conversation. If it later crashed uncleanly, ambient mode (whose whole documented purpose is exactly this retroactive safety net) would never revisit it. **The first fix attempt was itself found broken by a follow-up review**: a recency check (finalize only once quiet for a full lease window) still fails for anyone paused *longer* than that window (lunch, a meeting) and then resumed — no fixed-timeout heuristic can actually distinguish "paused" from "done." Fixed properly by never finalizing a too-short session at all: left `Leased`, naturally reclaimable forever at near-zero cost.
4. One Medium-severity fix alongside these: a synchronous, file-I/O-heavy `run_memory_md_consolidation()` call was blocking a Tokio worker thread directly inside an async task — moved onto `tokio::task::spawn_blocking`.
